## Is it still relevant under pay-first?

Yes. Pay-first makes waive rarer, not less wrong. Under pay-first, waive is the ONLY way a non-HMO visit releases without money (goodwill, staff/family, charity, or a write-off after a payment was deleted). Every such release today leaves the waived amount sitting in 1100 as a receivable that will never be collected and in revenue at full price. Frequency on prod is zero because nothing is live yet, not because the path is unused by design. The fix is small and the defect is permanent per occurrence, so it earns its place.

## What the brief does not cover (additions)

1. **Legacy visits must stay GL-silent when waived.** This morning's item 8 proposes waiving the 6 legacy owing visits. Their release and payment rows never posted (bridge skips `legacy_import_run_id`), so 1100 holds nothing for them. A waiver JE that debits 4910/4920 and credits 1100 for a legacy visit would create a phantom credit in 1100 and a phantom discount. The waiver bridge must skip visits with `legacy_import_run_id is not null` (or, more robustly, post only against AR actually booked: sum of posted release JE debits to 1100 for the visit's lines minus posted payment credits).
2. **Fold the waived share into the release JE rather than posting a separate waiver entry, for the common waive-before-release case.** Since release is blocked while unpaid, the normal order is waive → release. At release time the bridge already knows the visit is waived; it can post DR 1100 for the paid share, DR 4910/4920 for the waived share, CR revenue full, in the ONE release JE keyed by the test_request. Benefits: no new source kind, no double-post on replay (the existing one-posted-per-source index covers it), and the released→cancelled bridge mirrors the JE's lines so cancellation reverses the waiver share for free. A separate waiver JE at waive time would credit 1100 before it was ever debited (negative AR until release, or forever if the visit never releases or a line is deleted).
3. **Allocation rule for partial payments.** Payments are not allocated to lines. Proportional allocation per line (`final_price × remainder / total`) is the only deterministic rule; state it, round per line, and push the centavo residue onto the last line so the visit's waived total equals `total - paid` exactly. Doctor lines go to 4920, everything else to 4910.
4. **Waive-after-release still needs a separate JE.** Reachable in the #228 world: released while paid → payment deleted (now unpaid) → admin waives. Here the release JE already debited 1100 in full, so a waiver JE DR 4910/4920 / CR 1100 for the remainder at waive time is correct. Key it by visit (`source_kind='visit_waiver'`, `source_id=visit_id`) under the one-posted-per-source index. Posting date = Manila date of the waive (0140 rule). A closed accounting month must refuse (je_period_lock_check, P0002) and the action must surface that. Waive cannot be undone (no un-waive action; recalc preserves waived), so no reversal path is needed unless a later line cancellation reverses part of a release JE that this waiver JE assumed — then the visit's 1100 goes negative by that line's share. Decide: either block cancellation on waived visits after the waiver JE exists, or have the cancel bridge reverse a proportional slice of the waiver JE. The simpler rule is to block.
5. **Payments on a waived visit: refuse at the database, not only in the page.** A payment on a waived visit credits 1100 again while the waiver already cleared it, so 1100 goes negative for that visit; and the status stays waived so nothing in the UI would show the money. The visit page already hides the button; the Record payment action must refuse, and per the skill's rule that UI checks are UX only, add a DB guard (new P-code + `pg-errors.ts` translation + coverage test) on `payments` insert when the visit is waived. The page copy uses `waivedAmount`.
6. **Ordering with the approved #228 follow-up PR.** No file overlap in code; both may touch the `drmed-payments` skill and the user guide. Run them in separate worktrees; whichever merges second rebases the skill/guide edits. The waiver PR carries a migration; the other does not.
7. **Split visits** (`visit_group_id`): waive is per visit, each half is its own ledger unit; nothing extra, but the smoke should include a split pair with one half waived.
8. **Backfill**: none (0 waived on prod, verified 2026-09-25). The migration must still be safe if a waived visit appears between prod push and deploy: the DB bridge, not the app, does the posting, so that window is covered.

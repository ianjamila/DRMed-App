# Corrected-result follow-ups — design

Date: 2026-09-25 · Branch `feat/result-copy-followups` (off `9af94b4b`) · Follows #223 (0172) and #226 (0176).
One PR, one migration (number claimed at build with `npm run -s claim -- migration`; P-codes with `pcode N` if any are raised).

## Why

A released structured result can now be corrected (0172), and the patient portal marks a result the patient downloaded before the correction (0176). Nothing yet helps the clinic act on a correction: nobody sees which patients still hold the old copy (portal download **or** a printed hand-over), the patient can't be told, reception can re-hand an old printout, and a correction silently deletes the critical alerts it removed.

Prod on 2026-09-25: 12 results, 0 corrections, 0 critical alerts, 2 patient downloads. This work is protective, so it favours clear rules and low-risk data changes over heavy reporting.

## Owner decisions (2026-09-25)

1. **Data export** keeps stripping every staff-written reason / note / remark / comment / `prior_values`, and lets known **system codes** through (today `visit_created`, `manual_reissue` on `visit_pin.*`). Edit, undo-release and deletion reasons stay hidden.
2. **Patient notification is per correction, opt-in.** The edit form offers "Let the patient know an updated copy is ready", default **off**, and only when the patient holds a copy. The message never includes the reason. There is no automatic notification (the earlier "no patient notification" default holds unless staff tick the box).
3. **The out-of-date copies list belongs to reception + admin.** No reasons, no values. Lab roles do not see it.
4. **Extras in scope:** print warning, v1-vs-v2 comparison, withdrawn-alerts history. **Out of scope:** pathologist re-sign-off after a correction.

## Definitions

- **Latest correction** of a result = its `result_amendments` row with the highest `seq`. `amended_at` = that row's timestamp; current version = `amendment_count + 1`.
- **Holds a portal copy out of date**: `results.patient_last_downloaded_at < latest amended_at` (microsecond compare, as `isUpdatedSinceDownload`).
- **Holds a printed copy out of date**: the newest `result.printed_staff` audit row for the result stamps `metadata.amendment_count` < current `amendment_count`, and no print of the current version exists. A row with no version stamp never counts (the `print-summary.ts` rule).
- **Followed up**: the latest correction has `patient_contacted_at`, **or** `patient_notified_at` with no `patient_notify_error`. An older correction's follow-up does not clear a newer one.

## 1. Data (the one migration)

`result_amendments` gains:

| Column | Meaning |
|---|---|
| `patient_contacted_at timestamptz`, `patient_contacted_by uuid → auth.users` | Staff marked the patient contacted about this correction |
| `patient_notify_requested boolean not null default false` | The editor ticked the checkbox |
| `patient_notified_at timestamptz`, `patient_notified_channels text[]`, `patient_notify_error text` | Send claim, outcome, and failure text (clinic-only) |

`critical_alerts` gains `withdrawn_at timestamptz`, `withdrawn_by uuid → auth.users`, `withdrawn_by_amendment uuid → result_amendments(id)`. The unacknowledged partial index is rebuilt with `withdrawn_at is null`.

`result_edit_commit` is redefined: the 0176 body plus marked hunks, generated by script from the 0176 text like 0176 was from 0172. (a) The alert reconciliation **updates** a removed unacknowledged alert to withdrawn instead of deleting it. (b) It stores `p_notify_patient` in `patient_notify_requested`. (c) The alert identity match for "kept" and "re-page" ignores withdrawn rows. `commit_outcome` keeps its shape; `alerts_removed` now counts withdrawals. The **finalise** path's cleanup of pre-0172 leftovers (`0172` line ~534) stays a delete, because it is not a correction.

New RPCs:

| RPC | Who | Returns / does |
|---|---|---|
| `result_outdated_copies(p_include_followed_up boolean default false)` — security definer | reception, admin (else 42501) | One row per result whose latest correction is not followed up and whose patient holds an out-of-date copy: result id, visit id, patient name + DRM id + phone + email presence, test / report name, latest `amended_at`, copy kind (`portal` / `printed` / `both`), notify state. **No reason, no values, no editor-written text.** |
| `result_mark_copy_contacted(p_amendment_id uuid)` — security definer | reception, admin | Sets contacted at/by on that amendment if it is still the latest, and is idempotent; audited `result.patient_contacted`. P-code if the amendment is not the latest. |
| `result_claim_patient_notify(p_amendment_id uuid)` — service_role | server only | `update … set patient_notified_at = now() where id = … and patient_notify_requested and patient_notified_at is null returning …`: the send claim. It returns nothing on a second call, so a retry or replay never sends twice. |
| `result_record_patient_notify(p_amendment_id, p_channels text[], p_error text)` — service_role | server only | Records the channels that went out, or the error. The claim stamp stays set either way, so nothing re-sends (not even a replayed edit); a failed send (`patient_notify_error` set) keeps the row on the list as "Send failed" for a phone call. |

Grants follow the 0119 / born-closed conventions: revoke from public/anon, grant only the listed roles, and pin them in a migration test.

## 2. Out-of-date copies list (reception + admin)

- **Page** `/staff/results/outdated-copies` (reception + admin, nav placement per `drmed-staff-ui`): a table of patient, phone, test/report, "Corrected <when>", copy kind, notify status ("Notified by email/SMS <when>", "Send failed", "Not notified"), a **Mark as contacted** button, and a link to the visit. A "Show followed-up" toggle.
- **Dashboard card** for reception and admin: "Patients with an out-of-date copy (N)" → the page. Hidden at 0, matching sibling cards.
- **Visit page chip** on the result row: "Corrected <date> — patient has an older copy" (portal/printed wording), with no reason. The same data comes from a narrow per-visit RPC variant or a filter of the list RPC, so reception never needs `result_amendments` read access.

## 3. Tell-the-patient checkbox

- It is shown on both edit forms (single test and consolidated chemistry) only when the patient holds a copy (portal download or printed hand-over, as above) **and** has an email or mobile on file. Otherwise it is absent, with a short hint why.
- After `commitResultEdit` confirms the commit (including a replayed or probed commit), the server calls `result_claim_patient_notify`. Only if that returns a row does it send, then it records the outcome.
- **Message:** reuse the `notify-released.ts` builders and branded email with new copy: "An updated copy of your <test> result is ready. You can view and download it securely in the patient portal." SMS in the same tone. No reason, no values. Audited `result.notified` with `kind: "corrected"`.
- A send failure never fails the edit. The editor sees "Saved — the patient message could not be sent", and the list shows "Send failed".

## 4. Print warning

When the newest print of a result is an older version, Print on the visit page, the queue's Released-today card and the Results archive warn "Printed copy is v1 — the current version is v2. Reprint before handing over." This reuses `print-summary.ts` and the served-version stamping from #223, and needs no new data.

## 5. What changed (v1 vs v2)

A staff-side comparison per correction: for each parameter whose value, flag or blank state changed, it shows parameter, old → new, and flag old → new. Old = the amendment's `prior_values_json`; new = the next amendment's snapshot, or current `result_values` for the latest. PDF-only corrections say "File replaced; values unchanged". It is gated by `staff_can_read_finished_result`, is never shown to reception, and is never shown in the portal. It sits in the History block of `queue/[id]`, the consolidated page and each chemistry report card, as an expandable "What changed" under each "Updated …" remark. It is pure TS (`diffResultVersions`) with unit tests.

## 6. Withdrawn alerts history

- Every **active-alert** read filters `withdrawn_at is null`: the bell/realtime, Critical Alerts page, dashboard counts, the paging path and the edit's own reconciliation. The plan enumerates each call site by grep for `critical_alerts`.
- The Critical Alerts page gets a "Withdrawn" view/section: "Withdrawn by correction on <when> by <who>", linking to the result. Acknowledge is not offered on withdrawn rows.
- `result.critical_alert_withdrawn` auditing stays.

## 7. Smaller items

- **Results archive** filters "Updated this week" and "Updated by me", with the latest correction in the Manila half-open week window (`manilaRangeUtc`) and `amended_by = me`. They are read through the signed-in client so `result_amendments` RLS scopes them.
- **Lab dashboard** "Updated this week (N)" count linking to the filter.
- **Audit Log quick filter** "Result corrections": `result.amended`, `result.critical_alert_withdrawn`, `result.patient_contacted`, `result.notified` (corrected).
- **Every-member section check** (`canViewResultPdf({ memberSections })`) on the archive's "PDF →" link and the chemistry report card's View PDF, so the links only offer what the route serves.
- **Export allowlist**: `patientSafeAuditRows` keeps a scrubbed key when its value is in a fixed set of system codes (`visit_created`, `manual_reissue`). Anything else under those keys is still dropped. Unit-tested both ways.

## Error handling

- The list and chip RPCs fail closed: an error shows "Couldn't load follow-ups", never an empty "all clear".
- Mark-as-contacted on a stale amendment returns the P-code, and the UI says "This result was corrected again — refresh".
- A notify claim or record failure is logged and shown; it never touches the committed edit.
- The alert migration backfills nothing (0 alerts on prod). Existing deletes before this PR stay in the audit log.

## Out of scope
